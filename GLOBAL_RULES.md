# СИСТЕМА AUTPOSTER — ГЛОБАЛЬНЫЕ ПРАВИЛА
Версия: 1.1
Статус: КАНОН

Этот документ — ЕДИНЫЙ ИСТОЧНИК ИСТИНЫ для системы AutoPoster.

---

# 1. НАЗНАЧЕНИЕ

Создать полностью автономную платформу автопостинга контента с:
- интеграцией Grok (через внешний API)
- публикацией в Telegram (через Bot API)
- полнофункциональным веб-интерфейсом администратора
- архитектурой планировщик/воркер на базе задач
- контролем исходящего VPN-трафика: запросы к Grok ДОЛЖНЫ идти через WireGuard

Система должна поддерживать:
- автоматическую генерацию и публикацию 24/7
- настраиваемые промпты по теме/слоту
- гибкое расписание по дням/времени/диапазонам дат
- несколько типов постов: text/photo/video/album/card
- строгий JSON-контракт от LLM
- надёжную безопасность и аудит
- нулевое ручное вмешательство после настройки

---

# 2. КЛЮЧЕВЫЕ ПРИНЦИПЫ

## 2.1 Конфигурационный подход (без хардкода)
Всё поведение ДОЛЖНО настраиваться через админ-панель:
- channels
- themes
- prompts
- schedules (дни/время/диапазоны дат)
- флаги включения/выключения
- часовой пояс
- лимиты публикаций
- retries, backoff, quiet hours

Конфигурация может храниться в БД. Файловая конфигурация допустима только для bootstrap.
После включения админки БД становится источником истины.

## 2.2 Строгий JSON-контракт (LLM)
LLM должен возвращать ТОЛЬКО JSON. Без markdown, без обёрток, без лишнего текста.
Невалидный JSON ДОЛЖЕН отклоняться, а задача помечаться ERROR с сохранением сырого ответа.

## 2.3 Обработка на базе задач
Каждая генерация/публикация — это Job.
Статусы задачи: NEW → RUNNING → DONE | ERROR
Публикация напрямую без записи Job запрещена.

## 2.4 Идемпотентность
Планировщик НЕ ДОЛЖЕН создавать дубликаты для одинаковых (channel_id, slot_id, scheduled_at).
Воркер ДОЛЖЕН быть безопасен к повторам.

## 2.5 Разделение ответственности
Модули:
- Scheduler
- Worker
- Grok Client
- Telegram Client
- Media Handler (опционально)
- Storage layer (PostgreSQL)
- Admin panel (UI + API)
- Security layer
- Audit/Logging

Нельзя смешивать обязанности.

## 2.6 Правило VPN-выхода (WireGuard)
Все исходящие запросы к Grok API ДОЛЖНЫ идти через WireGuard-туннель.

Реализация ДОЛЖНА поддерживать policy routing так, чтобы:
- Только воркер (или только запросы к хосту Grok) использовали wg0
- Telegram API и другой серверный трафик могли идти по маршруту по умолчанию (опционально и настраиваемо)

Система ДОЛЖНА давать инструкции для обеспечения:
- wg-quick up wg0
- ip rule / ip route (или cgroup-маршрутизация), чтобы трафик Grok шёл через wg0
- шаги проверки (curl, ip route get, tcpdump)

Воркер ДОЛЖЕН поддерживать один из механизмов (на выбор):
A) Запуск от выделенного Linux-пользователя (рекомендуется) + fwmark routing
B) Маршрутизация по домену/IP назначения (endpoint Grok) через table 51820
C) Запуск воркера в Docker-контейнере с сетью только через wg0

Предпочтителен вариант A.

## 2.7 Админ-панель прежде всего про безопасность
В админке ДОЛЖНЫ быть:
- хеш пароля bcrypt/argon2
- TOTP 2FA
- защита CSRF
- rate limiting (вход и чувствительные действия)
- secure cookies (HttpOnly, Secure, SameSite=Strict)
- строгие заголовки (CSP, XFO и т.д.)
- опциональный allowlist по IP
- аудит-лог действий администратора

Секреты ДОЛЖНЫ храниться в env и никогда не печататься.

## 2.8 Правила публикации в Telegram
Публикация только через Telegram Bot API.
Бот должен быть администратором канала с правом публикации.

## 2.9 Типы постов
Система должна поддерживать:
- text: sendMessage
- photo: sendPhoto (caption)
- video: sendVideo (caption)
- album: sendMediaGroup
- card: sendMessage с кнопками InlineKeyboard (или photo+buttons)

Каждый тип ДОЛЖЕН быть реализован явно.

## 2.10 Правило качества веб-интерфейса («сделайте круто»)
Админка ДОЛЖНА быть:
- современный, чистый UI
- быстрая, адаптивная (desktop-first)
- детализированное управление
- визуальный редактор расписания (календарь + недельная сетка)
- drag-and-drop перестановка слотов
- редактор промптов с шаблонами и переменными
- предпросмотр поста (как он будет выглядеть в Telegram)
- JSON-редактор с валидацией и подсказками схемы
- дашборд задач с фильтрами, повтором, просмотром сырого ответа LLM
- логи и аудит-трейл

# 3. МОДЕЛЬ ДАННЫХ (минимум)

В PostgreSQL ДОЛЖНЫ быть как минимум:

- channels
- themes
- prompts (с версиями)
- schedules (правила и слоты)
- jobs
- admin_users
- admin_sessions (опционально)
- audit_log
- settings

БД является авторитетным источником данных выполнения.

---

# 4. ПРАВИЛА ПЛАНИРОВАНИЯ

Планирование должно поддерживать:
- часовой пояс
- слоты по дням недели
- переопределения по диапазону дат (кампании)
- исключения/blackout-периоды
- лимиты частоты по теме
- quiet hours (опционально)

Админ UI ДОЛЖЕН управлять этим визуально.

---

# 5. ОБРАБОТКА ОШИБОК

- Любая ошибка → задача ERROR с last_error
- Сохранять сырой ответ модели для отладки
- Стратегия повторов настраиваемая: max_attempts + backoff
- Ручной повтор из админ-панели

---

# 6. РАСШИРЯЕМОСТЬ

Добавление новой темы / слота расписания / промпта НЕ ДОЛЖНО требовать изменения кода.
Только конфигурация в UI.
